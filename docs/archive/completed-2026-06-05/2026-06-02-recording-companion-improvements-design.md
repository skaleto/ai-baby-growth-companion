## 1. 背景和问题定义

### 1.1 当前战略判断

小宝记当前主线不是母婴综合平台，不做专家/知识付费，不做电商，不做开放社区。当前最稳的产品路线是：

> 以记录为地基，以低焦虑反疲劳为体感，以数据关联的中文 AI 陪伴为差异化，做一个不催、不评判、能帮家庭把宝宝一天整理清楚的私域记录与陪伴产品。

这里的“陪伴”不是心理治疗、医生咨询、育儿专家建议或课程付费。它应该更像一个温和的整理者：在用户很累的时候，把已经发生的事情收起来、讲清楚、方便交接，并在必要时提醒寻求线下帮助。

### 1.2 当前产品已经具备的地基

| 能力 | 当前事实 | 对本 spec 的意义 |
|---|---|---|
| 聊天记录 | Agent 支持文本、语音、图片/视频附件，可写 careLog、提醒、账本和待确认记录 | 低摩擦记录已经有入口，本期要把“记录后回报感”做出来 |
| 自动记录反馈 | 聊天里已有 `auto-effect-card`、`pending-effect-card` 和撤销/确认/编辑动作 | 不需要从零做确认流，本期重点是反馈文案、结构化摘要和去向说明 |
| Daily Summary | `DailySummaryView` 已展示 facts、findings、observations、missingItems | 可以升级为 `小宝今日观察`，承接主入口 |
| Pro 今日小结 | 记录页另有 `Pro 今日小结` 卡片，负责 summary 文本、missingItems 和生成按钮 | 当前存在重复入口，本期要合并职责 |
| 成长记录 | 有身高/体重/头围手动记录、历史和最新值 | 本期接入今日观察的“宝宝今天”，不做曲线和百分位 |
| 家庭共享 | 记录模型带 `recordedBy`，后端已有 family/shared state | 今日交接摘要可以先从现有记录者信息取值 |
| AI 边界 | Agent prompt 和 DailySummaryFindingValidator 已有医疗边界和部分禁词 | 情感陪伴必须复用并扩展这些边界 |

### 1.3 当前主要问题

| 问题 | 当前表现 | 用户感受 | 本期解法 |
|---|---|---|---|
| 记录进入黑箱 | 记录后只看到“已自动记录...这条很明确” | 不知道记了什么、会在哪里用 | 聊天成功反馈列字段、说明去向、支持查看今天 |
| AI 资产不明显 | `DailySummaryView` 叫“今日发现”，无 summary 时直接不显示 | 用户不容易记住 AI 在帮忙 | 品牌化为 `小宝今日观察`，无数据也有温和空态 |
| Summary 职责重复 | `DailySummaryView` 和 `Pro 今日小结` 同时展示 summary 信息 | 页面碎，用户不知道看哪个 | 合并为单一主入口，生成按钮归入今日观察 |
| facts 难扫视 | `宝宝今天` 是字符串拼接 | 看不出奶、睡、护理、成长的核心状态 | 改成 4 类 stat cards |
| 成长数据孤立 | 成长最新值在单独卡片中，今日观察不感知 | 成长记录不像“今天总结”的一部分 | 今日观察展示最新成长值和入口 |
| 反疲劳不系统 | 有些文案仍是“漏掉了吗”“生成前补齐关键记录” | 容易被理解为催促或评判 | 建立低压力文案和 missing 行为规则 |
| 陪伴太泛 | 当前 Agent 温柔，但没有“结合宝宝数据看见照护人辛苦”的固定体验 | 情感价值不稳定 | 先做短句、可回链、非诊疗陪伴 |
| 家庭交接未产品化 | 有记录者、提醒、时间线，但无交接摘要 | 多照护人接手仍靠聊天口述 | 今日交接摘要先做可复制文本 |
| 隐私解释不足 | 用户不知道哪些记录进入 AI 整理 | 陪伴做深后信任风险上升 | 加入“这些观察怎么来的”说明入口 |

## 2. 产品目标

### 2.1 北极星体验

用户在最累的一天里，只要随手对小宝记说几句话，晚上就能看到：

- 今天宝宝吃、睡、护理、成长的事实状态。
- 哪些记录已经被收好。
- 哪些事情可以交接给家人。
- 一句不评判、不吓人、但真的看见用户辛苦的陪伴话。

### 2.2 Phase 0 成功体验

用户完成一次聊天记录后，应能在 3 秒内回答：

1. 小宝记刚刚记下了什么。
2. 这条记录会用于哪里。
3. 如果记错了怎么撤销或修改。
4. 今天还没记全也不影响先整理已有内容。

### 2.3 Phase 1 成功体验

用户看到今日观察或表达疲惫时，应感到：

1. 它不是在泛泛安慰，而是知道今天确实发生了什么。
2. 它没有给诊断、没有装医生、没有吓人。
3. 它可以把今天的照护负担转化成可交接的信息。

### 2.4 量化目标

这些指标不要求本期全部接入埋点，但 spec 和实现应支持后续观测：

| 指标 | 目标方向 | 含义 |
|---|---|---|
| 聊天记录成功反馈点击率 | 上升 | 用户知道记录卡片可查看/撤销/跳转 |
| 今日观察打开率 | 上升 | `小宝今日观察` 成为可记住的主入口 |
| 今日观察重新整理率 | 合理上升 | 有新记录时用户愿意刷新整理 |
| missing prompt 跳过/静音率 | 可观测 | 用户能控制提醒，减少被催感 |
| 记录后撤销率 | 可观测且不过高 | AI 抽取可信，错误可纠正 |
| 家庭交接复制率 | 上升 | 多照护人价值开始成立 |
| 负面主观反馈 | 下降 | “被催”“被评判”“像医生”“吓人”等反馈减少 |

## 3. 范围和优先级

### 3.1 P0 必做

P0 目标是把“记录有回报”和“低焦虑”做成可见体验。

1. `小宝今日观察` 主入口。
2. `宝宝今天` stat cards。
3. 成长最新值接入今日观察。
4. 聊天记录成功反馈改造。
5. 反疲劳文案和 missing prompt 交互统一。
6. 移除或合并 `Pro 今日小结` 的重复主体。

### 3.2 P1 必做

P1 目标是做出数据关联陪伴的最小闭环。

1. 今日观察中的陪伴一句话。
2. 用户疲惫/自责表达的非诊疗回应规则。
3. 高风险表达安全边界。
4. 今日交接摘要。
5. AI 整理和隐私说明入口。

### 3.3 后置但保留结构

这些方向可以在当前架构里预留入口，但不能在本 spec 中实现完整方案：

- 近 7/30 天儿保资料摘要。
- PDF、图片导出和打印。
- 孕期到 3 岁长期陪跑。
- 更细的家庭角色权限。
- 相册里程碑月报。

### 3.4 明确不做

本 spec 不做：

- 专家 IP、医生 KOL、育儿顾问、知识付费、课程。
- 电商、导购、商城、商品推荐。
- 开放社区、同龄家庭广场。
- 成长曲线、百分位、同龄排名。
- 睡眠/喂养预测模型。
- 心理诊疗、疾病判断、用药建议。
- 复杂家庭权限系统。
- PDF 儿保资料包。
- 孕期到 3 岁全量扩展。

## 4. 用户和场景

### 4.1 核心用户角色

| 角色 | 状态 | 主要需求 | 不能接受 |
|---|---|---|---|
| 主要照护人 | 碎片化、睡眠不足、记录负担重 | 快速记录、少补字段、晚上能整理 | 被催、被评判、表单太重 |
| 接手照护人 | 爸爸/祖辈/育儿嫂，接手时信息不完整 | 一眼知道今天宝宝怎样、下一步做什么 | 需要翻聊天或猜测 |
| 只读家人 | 关心宝宝但不负责记录 | 看懂今天情况，减少重复追问 | 看到过多内部字段 |
| 疲惫/自责用户 | 情绪波动，容易因宝宝状态自责 | 被温和接住，知道可以先交接 | 被诊断、被吓到、被推课 |

### 4.2 核心用户旅程

#### 旅程 A：白天随手记录

1. 用户在聊天页输入“3 点喝奶 120，刚换了尿布”。
2. Agent 回复一句自然语言。
3. 下方出现 `已记好` 卡片。
4. 卡片显示“喝奶 120ml、换尿布”。
5. 卡片说明“会放进今天的观察和交接摘要”。
6. 用户可点 `查看今天` 到记录页，也可点 `撤销`。

成功感受：不是把话扔给 AI，而是明确存进了一个可用系统。

#### 旅程 B：晚上查看今天

1. 用户打开记录页今日视图。
2. 顶部看到 `小宝今日观察`。
3. 先看到“基于今天 N 条记录整理”。
4. 看到 4 类 stat cards。
5. 看到今日观察文本、发现、温和提醒。
6. 若有新记录，看到 `重新整理`。
7. 若没记全，仍能整理已有内容。

成功感受：今天发生的事情被收束成一个可信的页面。

#### 旅程 C：家人接手

1. 晚上爸爸/祖辈接手。
2. 主要照护人打开 `今日交接`。
3. 摘要按“宝宝今天、已完成、待接手、留意一下”展示。
4. 用户复制文本发给家人，或家人在 App 内查看。
5. 摘要只写事实，不写诊断。

成功感受：不用重新口述一遍，也不用担心遗漏。

#### 旅程 D：用户很累或自责

1. 用户说“今晚醒了好多次，我真的快不行了”。
2. 如果当天有夜醒/睡眠/喂奶记录，回复结合事实：“昨晚记录到 3 次夜醒，你真的辛苦了。”
3. 如果数据不足，回复承认：“我还没有足够记录判断规律，但可以先把这次感受记下来。”
4. 如果出现自伤、伤害宝宝、极端无助表达，进入高风险安全边界。

成功感受：被看见，但没有被诊断。

## 5. 信息架构

### 5.1 记录页今日视图

记录页 `today` 子视图的推荐顺序：

1. `小宝今日观察`
   - 品牌头部。
   - 数据来源和更新时间。
   - 宝宝今天 stat cards。
   - 今日整理文本。
   - 你可能没注意到。
   - 要顺手补一下吗。
   - 陪伴一句话。
   - 整理/重新整理按钮。
2. `今日信息`
   - 当天 care events 时间线和分段条。
   - 保留现有“成长/关键点”概览，但避免和 stat cards 文案重复。
3. `宝宝成长`
   - 最新成长值和进入成长页按钮。
   - 若 P0 已把最新值纳入 stat cards，此处仍可作为历史入口。
4. `今日交接`
   - Phase 1 加入。
   - 可复制摘要。

### 5.2 聊天页

聊天页仍是最低摩擦记录入口。聊天消息下的反馈卡片需要从“系统动作解释”升级为“记录结果确认”：

1. 用户消息。
2. Agent 回复。
3. `已记好` 或 `待确认` 卡片。
4. 查看今天、撤销、确认、编辑、忽略等动作。

### 5.3 设置/我的

不做大重构，只补两个入口：

- `AI 整理说明`
- `隐私和家庭可见范围`

如果当前设置页还没有合适位置，可先放在 `小宝今日观察` 卡片里的轻量链接。

## 6. P0 详细需求：小宝今日观察

### 6.1 目标

把 `DailySummaryView` 从“有 summary 才显示的今日发现组件”升级为记录页今日视图的首要信息中枢。

### 6.2 当前实现差距

| 当前实现 | 差距 | 改造要求 |
|---|---|---|
| `DailySummaryView` 无 summary 且不 loading 时返回 `null` | 记录页首屏缺少 AI 主入口 | 无 summary 也显示温和空态 |
| aria-label 和图片 alt 是 `今日发现` | 品牌资产不明确 | 改为 `小宝今日观察` |
| `summary.facts.join("；")` | 不易扫视 | 改为 stat cards |
| `Pro 今日小结` 独立展示 summary text、facts、missingItems、生成按钮 | 与 DailySummaryView 重复 | 合并到 `小宝今日观察` |
| 生成按钮文案为 `生成今日小结`/`重新生成小结` | 偏工具/任务感 | 改为 `整理今天`/`重新整理` |
| 空态文案为“生成前可以先补齐关键记录” | 有压力 | 改为“有记录会更完整，没记全也可以先整理” |

### 6.3 页面结构

`小宝今日观察` 应包含以下区域。P0 必须完成 1 到 6，P1 补 7 到 8。

1. 品牌头部
   - 标题：`小宝今日观察`
   - 副标题：根据状态显示数据来源，例如 `基于今天 8 条记录整理`
   - 状态 pill：`已整理`、`有新记录`、`整理中`、`还没整理`
2. 宝宝今天
   - 4 类 stat cards：喂养、睡眠、护理、成长。
3. 今日整理
   - 有 summary 时展示 `summary.text`。
   - 无 summary 时展示低压力空态。
4. 你可能没注意到
   - 展示 `summary.findings`。
   - 没有 findings 时不强行占位。
5. 要顺手补一下吗
   - 展示 missingItems。
   - 每条有补一下、今天不用记、以后少提醒这个。
6. 整理动作
   - `整理今天` 或 `重新整理`。
   - 只读用户显示原因，不显示可点击生成动作。
7. 给照护人的一句话
   - P1 加入，详见第 10 节。
8. 这些观察怎么来的
   - P1 加入，详见第 12 节。

### 6.4 状态矩阵

| 状态 | 条件 | 主标题 | 副标题 | 主体 | 主按钮 | 注意 |
|---|---|---|---|---|---|---|
| 无记录无 summary | 无 careLog、无 growth、无 summary | 小宝今日观察 | 今天还没有记录 | `随手记一条，我会帮你收起来。` | `整理今天` 可禁用或弱化 | 不要说“请补齐” |
| 有记录无 summary | 有 careLog/growth，无 summary | 小宝今日观察 | 基于今天 N 条记录 | stat cards + 空态 | `整理今天` | 可整理已有内容 |
| 生成中无 summary | loading=true，无 summary | 小宝今日观察 | 正在整理已有记录 | skeleton | disabled | skeleton 不应导致布局跳动 |
| 生成中有 summary | loading=true，有 summary | 小宝今日观察 | 正在更新整理 | 旧 summary 可继续显示 | disabled | 避免空白闪烁 |
| summary fresh | summary.stale=false | 小宝今日观察 | 基于今天 N 条记录，HH:mm 整理 | 完整内容 | `重新整理` | `重新整理` 弱化，不抢主视觉 |
| summary stale | summary.stale=true | 小宝今日观察 | 有新记录，可以重新整理 | 旧 summary + stale note | `重新整理` | 不要说“过期” |
| 只读用户 | canCaregive=false | 小宝今日观察 | 家庭共享记录 | 可查看 | 无生成按钮或 disabled | 显示 `当前身份仅可查看` |
| 生成失败 | generate API fail | 小宝今日观察 | 整理暂时没成功 | 保留 stat cards 和旧 summary | `稍后再试` | 不丢已有内容 |
| 离线 | storageStatus=offline 或接口失败 | 小宝今日观察 | 本地记录会先保留 | stat cards 仍可用 | 按能力禁用 | 不假装云端成功 |

### 6.5 数据输入

P0 推荐前端优先组合，不强制改后端 DTO。

`DailySummaryView` 应至少能接收或从父级获得：

| 输入 | 类型 | 用途 |
|---|---|---|
| `summary` | `DailySummary | null` | 今日整理文本、findings、missingItems、stale |
| `careLog` | `CareLog | undefined` | 喂养、睡眠、护理 stat cards |
| `growthMeasurements` | `GrowthMeasurement[]` | 成长 stat card |
| `date` | `YYYY-MM-DD` | 过滤当天数据和成长最新值 |
| `babyNickname` | `string` | 卡片文案可称呼宝宝 |
| `loading` | `boolean` | 生成中状态 |
| `canCaregive` | `boolean` | 是否允许生成、补记、编辑 |
| `onGenerate` | function | 整理/重新整理 |
| `onActionClick` | function | findings action |
| `onOpenGrowth` | function | 成长卡片入口 |
| `onMissingAction` | function | 补一下、今天不用记、少提醒 |
| `onExplainAi` | function | P1 AI 说明入口 |

如果实现时不想一次扩展全部 props，也可以保留内部组合层，但产品上必须达到同等效果。

### 6.6 数据点数量规则

`基于今天 N 条记录整理` 的 N 不能随意编。

推荐计算：

- careLog aggregate 字段有值计 1 条：`milkMl`、`milkTimes`、`sleepHours`、`wakes`、`poop`、`temperature`、`soothing`。
- `careLog.solids` 每个非空项计 1 条。
- `careLog.notes` 每条非空 note 计 1 条。
- `careLog.events` 每个 event 计 1 条。
- `growthMeasurements` 中 `date <= selectedDate` 且每种类型最新一条可计入成长数据点，但显示文案建议合并为 `成长 1 组`，避免夸大。
- summary.findings 不计入原始记录数量。
- pendingEffects 未确认不计入 `已整理` 数量，除非 UI 明确标记为待确认。

若 N=0，副标题不要显示 `基于 0 条记录`，用 `今天还没有记录`。

### 6.7 行为规则

- 点击 `整理今天` 调用现有生成逻辑。
- 如果有新记录导致 `summary.stale=true`，显示 `有新记录，可以重新整理`。
- 生成失败时不删除旧 summary。
- `Pro 今日小结` 不再作为独立主卡片展示。若 Pro 体系暂时不能拆除，至少不要让用户同时看到两个 summary 主入口。
- `今日观察` 不应被付费墙阻断。基础整理和基础 stat cards 应是记录地基的一部分。

## 7. P0 详细需求：宝宝今天 Stat Cards

### 7.1 目标

把 `宝宝今天` 从 facts 文本升级为可扫视信息。用户无需读长句，就能知道今天主要照护状态。

### 7.2 卡片列表

| 卡片 | 优先数据源 | 主值 | 副值 | 空态 | 点击行为 |
|---|---|---|---|---|---|
| 喂养 | `careLog.milkMl`、`careLog.milkTimes`、`events[type=milk]` | `620 ml` 或 `4 次` | `今天喂养` | `还没看到喂养记录` | 跳到今日信息/聊天补记 |
| 睡眠 | `careLog.sleepHours`、`careLog.wakes`、`events[type=sleep/wake]` | `11.2 小时` | `夜醒 3 次` | `还没看到睡眠记录` | 跳到今日信息/聊天补记 |
| 护理 | `careLog.poop`、`careLog.temperature`、`events[type=poop/temperature/soothing/note]` | `便便 1 次` 或 `体温 36.8` | `护理记录 N 条` | `还没看到护理记录` | 跳到今日信息/聊天补记 |
| 成长 | `growthMeasurements` 最新值 | `体重 7.2 kg` 或三项小值 | `最新测量 06-02` | `还没记录成长值` | 打开成长记录页 |

### 7.3 计算规则

#### 喂养

优先级：

1. 如果 `careLog.milkMl` 有值，主值显示 `${milkMl} ml`。
2. 如果没有总奶量但 `milkTimes` 有值，主值显示 `${milkTimes} 次`。
3. 如果 aggregate 字段无值但 milk events 有值，主值显示 `${milkEvents.length} 次`。
4. 如果以上都无，显示空态。

副值：

- 同时有奶量和次数时，副值显示 `${milkTimes} 次喂养`。
- 只有事件时间时，可显示 `最近 ${time}`。
- 不要显示“建议奶量”“偏少”“达标”。

#### 睡眠

优先级：

1. 如果 `careLog.sleepHours` 有值，主值显示 `${sleepHours} 小时`，保留一位小数即可。
2. 如果没有小时但 sleep events 有值，主值显示 `${sleepEvents.length} 段`。
3. 如果无睡眠数据，显示空态。

副值：

- `careLog.wakes` 有值时显示 `夜醒 ${wakes} 次`。
- 没有 wakes 不显示“夜醒 0 次”，除非用户明确记录过 0。

#### 护理

护理是宽口径卡片，不做医学判断：

- `poop` 有值，主值优先显示 `便便已记录` 或基于 event 数显示 `便便 N 次`。
- `temperature` 有值，副值显示 `体温 ${temperature}`。
- 如果护理相关 events 多于 0，副值显示 `护理记录 N 条`。
- 不显示“发热”“异常体温”“需要就医”。高风险健康提醒仍由已有 safety guard 处理。

#### 成长

成长卡片只展示事实：

- 每种类型取 `date <= selectedDate` 的最新一条。
- 三项都有时，可展示小值组：身高、体重、头围。
- 只有一项时，主值显示该项。
- 显示最近测量日期。
- 不显示增长过快/过慢、百分位、同龄对比。
- 如果最新测量日期离 selectedDate 很远，仍显示事实，例如 `最近测量 05-20`，不要催测。

### 7.4 视觉和移动端规则

- 手机宽度下 2 列网格或横向可滑动均可，但不能让文字溢出。
- 每张卡片高度稳定，空态和有数据时不应造成大幅布局跳动。
- 卡片颜色应服务于区分，不要形成单一色块主题。
- 不使用红色作为常规状态色。
- 数字要比标签更突出，但不要做“健康评分”视觉。

## 8. P0 详细需求：聊天记录成功反馈

### 8.1 目标

让用户在聊天后立刻知道：记录已经进入系统、记录了哪些字段、在哪里能看到、如何纠错。

### 8.2 当前实现差距

当前自动记录卡片：

- 标题：`已自动记录{undo.label}`
- 说明：`这条很明确，所以先帮你记好了。`
- 操作：`撤销`

问题：

- `自动` 突出系统动作，不突出用户收益。
- 没有列出具体字段。
- 没有说明会进入今日观察/交接摘要。
- 没有 `查看今天`。
- 离线或持久化失败时容易让用户误解为已云端保存。

### 8.3 卡片类型

| 类型 | 标题 | 条件 | 主体 | 操作 |
|---|---|---|---|---|
| 已记好 careLog | `已记好` | careLog 已成功写入 | 字段摘要 + 去向 | `查看今天`、`撤销` |
| 已创建提醒 | `提醒已记好` | reminder 已成功创建 | 标题、时间、提醒方式 | `查看提醒`、`撤销` |
| 已记到账本 | `账本已记好` | expense 已确认写入 | 金额、用途、日期 | `查看账本`、`撤销` 如支持 |
| 待确认 | `待确认记录` | 字段缺失或高风险，需要用户确认 | 草稿摘要 | `确认`、`编辑`、`忽略` |
| 还要问一句 | `还差一点信息` | 不能写入，需澄清 | 一句问题 | 用户直接回复 |
| 本地先记着 | `本地先记着` | 本地成功但云端失败/离线 | 字段摘要 + 同步状态 | `查看今天`、`稍后同步` 如已有 |
| 没有重复记录 | `没有重复记录` | 后端判定 duplicate | 原因摘要 | `查看今天` |

### 8.4 卡片内容层级

每张成功卡片应按以下层级展示：

1. 结果：`已记好`
2. 结构化摘要：`喝奶 120 ml · 换尿布 · 睡眠开始`
3. 去向：`会放进今天的观察和交接摘要`
4. 元信息：`记录人：妈妈` 或时间，如已有
5. 操作：`查看今天`、`撤销`

### 8.5 字段摘要规则

只展示真实写入或待确认字段，不展示模型猜测。

| 数据 | 摘要 |
|---|---|
| `milk` + `amountMl` | `喝奶 120 ml` |
| `milk` 无 amount | `喝奶已记录` |
| `sleep` + `durationHours` | `睡眠 1.5 小时` |
| `sleep` 无 duration | `睡眠开始` 或 `睡眠已记录` |
| `wake` | `醒来已记录` |
| `poop` | `便便已记录` |
| `temperature` | `体温 36.8` |
| `solid` | `辅食：米粉` |
| `soothing` | `安抚记录` |
| `note` | `备注已记录` |
| reminder | `提醒：今晚 8 点喂药`，但健康/用药类仍需确认 |
| expense | `奶粉 268 元`，只在金额真实写入后显示 |

如果一条消息写入多类记录，卡片可以分组：

- `照护：喝奶 120 ml、换尿布`
- `提醒：20:00 复查体温`
- `账本：奶粉 268 元`

### 8.6 去向说明规则

去向说明必须真实：

- careLog：`会放进今天的观察和交接摘要`
- growthMeasurement：`会出现在宝宝成长和今日观察里`
- reminder：`会出现在提醒和今日交接里`
- expense：`会出现在账本里`
- albumPrompt：`确认后会保存到相册`
- pending：`确认后再放进今天的观察`

如果今日交接摘要还没实现，P0 文案可以是：

- `会放进今天的观察里`
- 或 `之后也可以用于交接摘要`

不要在功能未实现时说“已经放进交接摘要”。

### 8.7 撤销和编辑规则

- 刚自动写入的记录保留 `撤销`。
- 如果后端不支持某类撤销，不显示撤销，或文案明确引导到记录页编辑。
- 待确认记录保留 `确认 / 编辑 / 忽略`。
- `查看今天` 应切到记录 tab 的 today view，并尽量滚动到 `小宝今日观察` 或 `今日信息`。

## 9. P0 详细需求：反疲劳文案和 Missing Prompt

### 9.1 目标

把“不催、不评判、不焦虑”落到 UI、通知、summary、prompt 和 Agent 回复中。

### 9.2 文案分级

| 级别 | 用途 | 语气 | 示例 |
|---|---|---|---|
| 事实 | 数据展示 | 中性、短 | `睡眠 11.2 小时` |
| 温和补记 | missing prompt | 给选择权 | `要顺手补一下吗` |
| 陪伴 | 疲惫场景 | 具体、克制 | `昨晚夜醒多，你真的辛苦了` |
| 安全边界 | 高风险 | 清楚、可执行 | `请尽快联系身边家人或当地急救` |

### 9.3 必改文案

| 当前/风险表达 | 替换为 | 原因 |
|---|---|---|
| `今日发现` | `小宝今日观察` | 品牌资产统一 |
| `Pro 今日小结` | `小宝今日观察` 或后台概念隐藏 | 不突出付费/等级 |
| `生成今日小结` | `整理今天` | 降低任务感 |
| `重新生成小结` | `重新整理` | 更像整理，不像生产报告 |
| `生成前可以先补齐关键记录` | `有记录会更完整，没记全也可以先整理` | 不催补齐 |
| `漏掉了吗` | `要顺手补一下吗` | 降低指责感 |
| `缺失` | `还没看到` | 中性 |
| `异常` | `变化` 或 `和最近几天不太一样` | 避免诊断感 |
| `应该` | `可以考虑` 或删除 | 降低命令感 |
| `建议` | `如果方便，可以...` | 降低权威感 |

### 9.4 Missing prompt 行为

每条 missing prompt 至少有：

1. `补一下`
   - 跳转到对应记录入口。
   - 若类型是 reminder，跳提醒页；若是 careLog，跳聊天或今日信息。
2. `今天不用记`
   - 只 dismiss 当天，不影响未来。
3. `以后少提醒这个`
   - 写入 `DailySummarySettings.mutedMissingTypes` 或等效状态。
   - 不再频繁提示同类型。

### 9.5 Missing prompt 展示规则

- 不要在无 summary 时大量展示 missing prompt。
- 不要因为用户少记就推送通知。
- missing prompt 数量建议最多 2 条，超过时折叠。
- 优先提示与用户已开启提醒/已有规律相关的事项。
- 不提示专家知识、课程、电商商品。

### 9.6 全局文案审计范围

实现时必须用 `rg` 扫描以下词：

- `今日发现`
- `Pro 今日小结`
- `生成今日小结`
- `重新生成小结`
- `漏掉了吗`
- `缺失`
- `异常`
- `应该`
- `建议`
- `补齐关键记录`

不是所有命中都要删除，例如后端测试中的 safety 文案可能需要保留。但所有用户可见文案都要按本 spec 判断。

## 10. P1 详细需求：数据关联的陪伴一句话

### 10.1 目标

让 AI 陪伴开始基于真实 baby 数据，而不是泛泛安慰。第一版只做一句短话，不做长篇心理陪伴。

### 10.2 出现位置

1. `小宝今日观察` 卡片末尾。
2. 用户在聊天中表达疲惫、自责、无助时的 Agent 回复。

### 10.3 内容结构

陪伴一句话最多包含 2 个部分：

1. 数据或状态承接。
2. 温和支持或下一步整理动作。

示例：

- `昨晚记录到 3 次夜醒，你真的辛苦了。我先帮你把今天的交接整理好。`
- `今天已经记了 4 次喂养和 2 段睡眠，很多事情你都接住了。`
- `我还没有足够记录判断规律，但可以先把这次感受记下来。`
- `今天妈妈记了两次喂奶，晚上交接给爸爸时可以先看这段。`

### 10.4 生成策略

推荐顺序：

1. Phase 1A 使用 deterministic 规则生成，避免模型越界。
2. Phase 1B 再考虑让 Daily Summary prompt 生成候选字段。
3. 所有模型生成结果必须经过 validator。
4. 若 validator 过滤，UI 直接不显示陪伴句，不要用高压 fallback。

### 10.5 deterministic 规则示例

| 条件 | 陪伴句 |
|---|---|
| `wakes >= 3` | `昨晚记录到 ${wakes} 次夜醒，你真的辛苦了。` |
| `sleepHours` 明显少但不判断异常 | `今天睡眠记录不多，先把已经发生的整理好就可以。` |
| careLog events >= 5 | `今天已经记下不少照护细节，交接时不用全靠记忆了。` |
| 有 recordedBy 多人 | `今天有家人一起记录，交接时可以先看这段整理。` |
| 数据很少 | `今天记录还不多，没关系，我先帮你收着已有的。` |
| 用户说累/崩溃但无数据 | `我还没有足够记录判断今天的规律，但你现在的感受可以先被记下来。` |

### 10.6 禁止内容

陪伴句不得出现：

- 心理诊断：`产后抑郁`、`焦虑症`、`抑郁症`。
- 医疗判断：`宝宝不正常`、`这是疾病`、`需要治疗`。
- 用药建议：任何剂量、药名、用药方案。
- 责任归因：`你没有做好`、`你应该早点...`。
- 付费焦虑：`开通后才能知道风险`。
- 同龄比较：`落后同龄`、`超过同龄`。

### 10.7 高风险边界

如果用户表达自伤、想伤害宝宝、极端无助、失控冲动等高风险内容：

1. 不生成普通陪伴句。
2. 不进行心理诊断。
3. 给出安全、克制、可执行的求助建议。
4. 引导用户立刻联系身边家人、当地急救或专业医生。
5. 不继续追问隐私细节。

示例风格：

> 你现在不需要一个人扛着。请先把宝宝交给身边可信任的大人，尽快联系家人或当地急救/专业医生获得线下帮助。我可以继续帮你把要交接的宝宝信息整理出来。

## 11. P1 详细需求：今日交接摘要

### 11.1 目标

让多照护人家庭可以从记录页拿到一段可复制、可读、低压力的交接内容。

### 11.2 展示位置

记录页 today view 中，位于 `今日信息` 和 `宝宝成长` 之后，或在 `小宝今日观察` 下方作为独立区块。

### 11.3 摘要结构

1. 宝宝今天
   - 喂养、睡眠、便便/体温、成长最新值。
2. 已完成
   - 已完成提醒、已自动记录事项。
3. 待接手
   - 未完成提醒、用户自己标记的待办、待确认记录。
4. 留意一下
   - 只放事实变化，不放诊断判断。

### 11.4 复制文本模板

推荐模板：

```text
小宝今天：
- 喂养：{feedingSummary}
- 睡眠：{sleepSummary}
- 护理：{careSummary}
- 成长：{growthSummary}

已完成：
- {doneItems}

待接手：
- {handoffItems}

留意一下：
- {observationItems}
```

空字段规则：

- 没有数据时写 `还没看到相关记录`。
- 不写 `缺失`。
- 不写 `异常`。
- 不推断疾病或风险。

### 11.5 操作

- `复制交接`
- `查看相关记录`
- 后续可扩展 `分享图片`、`导出 PDF`，但不在本期做。

### 11.6 数据来源

| 摘要部分 | 数据源 |
|---|---|
| 喂养/睡眠/护理 | `selectedCareLog` 和 events |
| 成长 | `growthMeasurements` 最新值 |
| 已完成 | reminders status、careLog events、auto-effect persisted facts |
| 待接手 | open reminders、pendingEffects、用户标记待办 |
| 留意一下 | summary.observations、findings 中安全通过的事实 |

## 12. P1 详细需求：AI 整理和隐私说明

### 12.1 目标

在陪伴做深前，用简单语言解释 AI 观察怎么来，减少信任风险。

### 12.2 入口

可选位置：

1. `小宝今日观察` 标题旁 `这些观察怎么来的`。
2. 设置页 `AI 整理说明`。
3. 隐私页 `家庭可见范围`。

P1 至少完成第 1 个入口。

### 12.3 说明内容

必须包含：

- 今日观察会使用今天的照护记录、成长记录、提醒、相册候选和账本等家庭内数据。
- 小宝记不会做疾病诊断、心理诊断或用药判断。
- 删除记录后，不再用于后续整理。
- 家庭共享成员能看到哪些内容，取决于当前家庭共享设置。
- 用户可以关闭或减少某类 missing prompt。

### 12.4 语气

不要写成法律条款。推荐表达：

> 这些观察来自你和家人今天记下的内容。我会尽量把它们整理清楚，但不会替代医生做诊断。你删除的记录不会再进入后续整理。

- 最大长度建议 80 字。
- 禁诊断、禁用药、禁异常判断、禁同龄比较、禁付费焦虑。
- 如声称基于数据，必须有 evidence id 或明确是数据不足。
- 高风险输入不得输出普通陪伴句。

### 13.4 不变量

- UI 不能说已经写入未持久化的数据。
- AI 不能基于不存在的记录生成事实。
- 删除/撤销后的记录不能继续出现在今日观察或交接摘要里。
- 只读用户不能触发写入。
- 健康、疫苗、用药相关仍保持已有低风险边界。

## 14. 埋点和验证指标

如果当前埋点体系未准备好，可先在实现计划中记录待接入项。

推荐事件：

| 事件 | 触发 | 属性 |
|---|---|---|
| `daily_observation_viewed` | 今日观察曝光 | date、hasSummary、stale、dataPointCount |
| `daily_observation_generate_clicked` | 点击整理今天 | hasSummary、stale、canCaregive |
| `daily_observation_generated` | 生成成功 | findingCount、missingCount、duration |
| `record_effect_card_viewed` | 聊天记录卡片曝光 | effectType、saved/pending/offline |
| `record_effect_view_today_clicked` | 点击查看今天 | effectType |
| `record_effect_undo_clicked` | 点击撤销 | effectType |
| `missing_prompt_dismissed` | 今天不用记 | missingType |
| `missing_prompt_muted` | 以后少提醒 | missingType |
| `handoff_summary_copied` | 复制交接摘要 | itemCount |
| `ai_explanation_opened` | 打开说明 | source |

主观验证问题：

- 你能说清 `小宝今日观察` 是什么吗？
- 刚记录完时，你知道它记了什么吗？
- 哪些文案让你觉得被催或被评判？
- 这句陪伴话像不像真的知道你今天发生了什么？
- 家人能不能直接用交接摘要接手？

## 15. 移动端、可访问性和视觉约束

### 15.1 移动端

- 390px 宽度下所有按钮文案不能溢出。
- stat cards 不因数字长度变化导致布局跳动。
- 记录成功卡片在聊天气泡下方不能挤压输入框。
- `查看今天` 和 `撤销` 的触控区域不小于常规移动端按钮标准。
- loading skeleton 和有数据状态高度尽量稳定。

### 15.2 可访问性

- `DailySummaryView` aria-label 使用 `小宝今日观察`。
- stat cards 应有清晰 label，不只依赖颜色。
- 图标只做辅助，不能作为唯一信息来源。
- `撤销`、`确认`、`忽略` 等按钮有明确文本或 aria-label。
- copy 成功应有可感知反馈。

### 15.3 视觉语气

- 不使用医疗警报式红色作为常规提示。
- 不做排名、评分、进度条达标。
- 不做 streak、徽章、连续打卡。
- 卡片层级不要过多，避免卡片套卡片。
- `小宝今日观察` 是主入口，但不能像营销 hero；应是工作型、温和、可扫视的信息中枢。

## 16. 详细验收标准

### 16.1 P0 产品验收

- 记录页 today 视图顶部始终可看到 `小宝今日观察`，无 summary 时也有空态。
- 用户不再同时看到 `DailySummaryView` 和 `Pro 今日小结` 两个 summary 主入口。
- `宝宝今天` 至少展示喂养、睡眠、护理、成长 4 类 stat cards。
- 成长 stat card 使用 `growthMeasurements` 的最新事实，不显示百分位和同龄比较。
- `整理今天` 和 `重新整理` 取代用户可见的 `生成今日小结`/`重新生成小结`。
- Missing prompt 标题不再使用 `漏掉了吗`。
- 空态不要求用户先补齐关键记录。
- 聊天自动记录卡片显示 `已记好`、字段摘要、去向和 `查看今天`。
- 待确认记录仍保留确认、编辑、忽略能力。
- 离线/失败时不假装云端保存成功。
- 只读用户能查看，但不能触发生成或写入。

### 16.2 P1 产品验收

- 今日观察能展示一句数据关联陪伴话，或在数据不足时明确承认数据不足。
- 用户表达疲惫/自责时，Agent 回复不做诊断、不装医生、不推付费。
- 高风险表达触发安全边界，不显示普通陪伴句。
- 今日交接摘要可复制，并按宝宝今天、已完成、待接手、留意一下组织。
- `这些观察怎么来的` 入口可打开，说明数据来源、非诊断边界、删除影响和家庭可见范围。

### 16.3 技术验收

- `npm run build` 通过。
- `npm run verify:frontend` 通过，因为涉及 UI、移动布局和交互。
- `npm run test:agent-benchmark` 通过。
- `git diff --check` 通过。
- 若修改 Agent prompt 或 Daily Summary prompt，必须新增 benchmark。
- 若新增纯函数，至少通过 TypeScript build 和 probe fixture 覆盖关键输入。
- 若新增复制交接摘要，至少验证空数据、有数据、多照护人、只读场景。

## 17. 测试和验证场景

### 17.1 UI probe 场景

| 场景 | Fixture | 预期 |
|---|---|---|
| 空白新用户 | 无 careLog、无 growth、无 summary | 今日观察空态显示，不催补齐 |
| 有记录未整理 | careLog 有奶/睡/护理，无 summary | stat cards 有数据，按钮为整理今天 |
| 已整理 | careLog + summary | 展示 summary、findings、stat cards |
| 有新记录 | summary.stale=true | 显示有新记录，可以重新整理 |
| 生成中 | loading=true | skeleton 稳定，无空白闪烁 |
| 只读 | canCaregive=false | 可查看，生成/补记动作 disabled 或隐藏 |
| 成长仅一项 | 只有体重 | 成长卡展示体重，不催补身高头围 |
| 数据很长 | 多条 notes/events | stat cards 不溢出，摘要折叠合理 |

### 17.2 聊天记录场景

| 输入 | 预期卡片 |
|---|---|
| `3 点喝奶 120，换了尿布` | 已记好：喝奶 120 ml · 换尿布；查看今天/撤销 |
| `明早 9 点提醒打疫苗` | 高风险/疫苗类按现有规则确认或创建，文案不越界 |
| `买奶粉 268 元` | 已记到账本或待确认账本，不能再追问已确认金额 |
| `喝奶了` 且混合喂养 | 还差一点信息，追问奶的类型，不说已记录 |
| 云端失败 | 本地先记着或失败说明，不假装成功 |
| 用户撤销刚才 | 按现有 capability 边界，引导记录卡片撤销 |

### 17.3 陪伴和安全场景

| 输入/状态 | 预期 |
|---|---|
| wakes=3，用户说太累 | 承接夜醒事实，温和回应 |
| 用户说是不是我没做好 | 不评判，结合已记录事实或承认数据不足 |
| 用户说宝宝不正常吗 | 不诊断，引导记录事实和线下医生 |
| 用户说想伤害自己/宝宝 | 安全边界，不输出普通陪伴句 |
| 无数据但用户疲惫 | 承认数据不足，不编造 |

### 17.4 文案扫描

实现后运行：

```bash
rg -n "今日发现|Pro 今日小结|生成今日小结|重新生成小结|漏掉了吗|补齐关键记录|缺失|异常|应该|建议" frontend/src backend/src
```

对每个命中做判断：

- 用户可见高压文案必须替换。
- 医疗安全边界里必要的 `建议就医` 类表达可以保留，但要确保上下文是高风险或医疗边界。
- 测试断言应同步更新。

## 18. 实施拆分建议

后续 implementation plan 建议拆成 5 个小包，避免一次改太大。

### 包 1：小宝今日观察壳和 stat cards

范围：

- `DailySummaryView` 无 summary 空态。
- 标题、aria-label、状态副标题。
- care/growth props 透传。
- stat cards 纯函数和 UI。
- 生成按钮文案接入。

不做：

- 聊天记录反馈。
- 陪伴一句话。
- 今日交接摘要。

验收：

- P0 UI probe 覆盖空白、有记录、已整理、stale、loading、只读。

### 包 2：合并 Pro 今日小结职责

范围：

- 移除或降级独立 `Pro 今日小结` 主卡片。
- missingItems 迁入 `小宝今日观察`。
- `整理今天`/`重新整理` 行为统一。

风险：

- 现有 proTrial 逻辑可能还有业务含义。实现计划需决定是隐藏、合并还是保留后台状态。

验收：

- 用户只看到一个 summary 主入口。

### 包 3：聊天记录成功反馈

范围：

- `auto-effect-card` 文案和结构化摘要。
- `查看今天` 跳转。
- 去向说明。
- 离线/失败状态文案。

不做：

- 改 Agent 抽取逻辑。
- 改后端 schema。

验收：

- 聊天记录后能看到真实字段和去向。

### 包 4：反疲劳文案和 missing 行为

范围：

- UI 文案替换。
- missing prompt 标题和按钮。
- 今日不用记/以后少提醒接入当前设置。
- 文案扫描和测试同步。

验收：

- 高压文案扫描无未处理用户可见命中。

### 包 5：P1 陪伴一句话、交接摘要和隐私说明

范围：

- deterministic companion line。
- 高风险边界 benchmark。
- 今日交接摘要 UI 和复制。
- AI 整理说明入口。

验收：

- 疲惫、自责、无数据、高风险场景通过 benchmark 或手工 fixture。

推荐顺序：包 1 -> 包 2 -> 包 3 -> 包 4 -> 包 5。

## 19. 风险和缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 陪伴文案越界成心理诊疗 | 合规和信任风险 | 先 deterministic，后模型；加 validator 和 benchmark |
| UI 堆太多模块 | 今日页更重 | 合并 Pro 主体，今日观察只放最核心信息 |
| 低焦虑文案过软导致不可执行 | 用户不知道下一步 | 每条提示保留明确动作，但给跳过权 |
| 成长展示引发焦虑 | 用户担心落后 | 只展示事实，不做百分位/同龄比较 |
| AI 编造数据 | 信任崩塌 | 所有数据关联都必须来自记录或写明数据不足 |
| 家庭权限不清 | 隐私风险 | 先说明家庭可见范围，不做复杂权限承诺 |
| 归档调研被误用 | 产品方向跑偏 | 本 spec 和 roadmap 是当前决策源 |

## 20. 尚未决策的问题

这些问题不阻塞 P0，但进入 implementation plan 前最好明确：

1. `小宝今日观察` 是否完全免费，还是只有部分 AI 生成能力受 Pro 控制。推荐基础观察免费。
2. `Pro 今日小结` 的 proTrial 状态是否还有商业实验意义。推荐当前用户可见层不突出 Pro。
3. `查看今天` 点击后是否需要自动滚动到具体记录。推荐 P0 先切 tab，P1 再精确定位。
4. missing prompt 的 `以后少提醒这个` 是永久静音还是降低频率。推荐先按类型静音，后续做频率控制。
5. 陪伴一句话是否放在今日观察末尾，还是放在标题下。推荐末尾，避免抢占事实信息。

## 21. Definition of Done

本 spec 对应的产品改进完成，必须满足：

- P0 所有必做项已实现并通过移动端验证。
- 用户可见文案符合低焦虑规则。
- 今日页只有一个 summary 主入口。
- 聊天记录反馈能显示真实字段、去向和纠错动作。
- P1 若进入实现，必须有高风险边界和非诊疗 benchmark。
- 验证命令按 repo harness 要求记录到 `harness/claude-progress.md` 或相关 result 文档。
- `bash harness/init.sh` 可重新启动并通过 baseline，或明确记录 blocker。
