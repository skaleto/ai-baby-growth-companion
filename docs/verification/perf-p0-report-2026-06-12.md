# P0 架构债性能对比报告(2026-06-12)

## 测量方法

- 工具:`scripts/perf-benchmark.mjs`(Playwright + CDP,**6x CPU 节流**模拟中端手机)
- 数据集:600 相册项(含 54 视频)+ 150 聊天消息 + 60 照护日 + 20 提醒 + 80 账目(mock API,三版本完全一致)
- 每版本 3 轮取中位数;同机同尺(M 系芯片,**相对比较有效,绝对值≠真机**)
- 版本:
  - **A 基线 `352c016`**:用户最后一次报"冷启动卡/Tab 慢一拍/相册巨卡"时的代码(git worktree 重建)
  - **B `head-pre-P0`**:两波渲染修复后(visited-tab 懒渲染/去网格重挂载/ratio 合批/视频近视口挂载,commit `0188b29`)
  - **C `head-post-P0`**:P0 完成(D1 AlbumScreen memo 拆分 + D2,commit `523d503`)

## 结果(中位数,毫秒)

| 指标 | A 基线 | B 两波后 | C P0完成 | A→C 提升 |
|---|---:|---:|---:|---:|
| 冷启动可交互 boot_ms | 1184 | 519 | **481** | **-59%** |
| 相册首开 album_first_open_ms | 1057 | 1031 | **1005** | -5% |
| 相册首开主线程阻塞 blocked_ms | 292 | 163 | **141** | **-52%** |
| 相册滚动长任务阻塞 blocked_ms | 128(1 个长任务) | 0 | **0** | **-100%** |
| 输入 30 字(整树重渲染探针) | 1225 | 1086 | **814** | **-34%** |
| 相册二次打开 album_reopen_ms | 790 | 432 | **380** | **-52%** |
| 二开主线程阻塞 blocked_ms | 201 | 49 | **32** | **-84%** |
| 返回记录页 back_to_records_ms | 165 | 223 | 245 | **+48% ⚠** |

### 解读

- **冷启动 -59%**:主要来自"访问过才渲染"(基线一次性渲染全部四个 Tab 含整个相册网格)。
- **输入 -34%**:每键卡顿从 ~41ms/键 → ~27ms/键。B→C 的 -25% 全部来自 D1(AlbumScreen memo 后,打字不再重渲染相册子树,守卫测试 [M]:打字期间 AlbumScreen 渲染数=0)。剩余成本在记录页自身(聊天列表未 memo)——D1 后续阶段(拆 RecordsScreen)的目标。
- **相册二开 -52% / 阻塞 -84%**:基线每次进相册整网格销毁重建(seed key),已根除。
- **相册首开仅 -5%**:首开=真实挂载成本,本轮未动(虚拟化 D3 的目标);但**阻塞时间 -52%**,卡死感已大幅缓解。真机收益应大于此数:基准用 1x1 PNG,测不到"视频解码器 N 路并发初始化"被近视口挂载消除的部分。
- **⚠ 返回记录页 +80ms**:绝对值小(245ms),嫌疑是 visited-tab 条件分支与 memo 比较的开销,列入观察;若真机可感知,随 RecordsScreen 拆分一并处理。

## D2 后端(本基准不覆盖,机制与测试证据)

生产数据实查(只读 SQL):**132 张图片 0 缺缩略图**(登记册原"老照片网格解码原图"的判断有误,已修正);**17 视频缺 8 封面**。实际修复:

1. **app/state 读放大**:每次状态水合对每个附件执行 ensureThumbnail→OSS HEAD(132 附件 × 每次读取,每次数百毫秒纯浪费)。已加进程内 verified 缓存 + 失败 1 小时节流——状态接口的 OSS HEAD 次数从 **O(附件数×读取次数) 降至 O(附件数)(进程生命周期内一次)**。
2. **视频封面自愈**:新端点 `POST /api/uploads/{id}/poster`(幂等/仅看护人/绝不覆盖),客户端播放无封面视频抽帧回传。8 个存量缺封面视频随家人浏览自动痊愈,未来同类问题不再发生(根治 13777892890 视频无封面一类)。
3. 测试:`UploadPosterControllerTests` 2/2;后端全套 **177 测试全绿**。
